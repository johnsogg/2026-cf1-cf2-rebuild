# Functions

We've used functions throughout this entire text, and I've shown how to define
and use them, but we have not really gone deep.

You'll be happy to know that functions will help you organize your code so it is
easier to reason about, write, and troubleshoot.

## What's a function?

A function is a reusable routine that will accept optional input parameters,
execute some code based on those inputs, and optionally yield a result.

A quick recap of the function-definition syntax we first met in the syntax
chapter:

This is the syntax for _defining_ a function. All these parts are needed, every
time:

- The `function` keyword kicks it all off. This tells you and the Javascript
  interpreter that a new function definition is afoot.
- The function _name_ (in this example, `doMath`). You can use any name you
  like, but it pays to choose a good name so it stays legible.
- _Parentheses_ to delimit a comma-separated list of _parameters_. Even if the
  function doesn't take any arguments, you still need the parentheses. The
  parameters that you list here will assume whatever values you pass in. They're
  like private variables that only exist while your function is running.
- Curly braces to delimit the code that will run when the function is invoked.
  And this is also necessary, even if your function doesn't do anything yet.

A function is like a little recipe for doing some specific computation that can
be used by other code when it is needed. A function can be _used_ as many times
as needed, but it is only _defined_ once. So if you've written tall blocks of
code that repeats the same idea many times, now you can put that repetitive code
in one spot (the function), and then simply refer to it by name.

## Translating math to a code function

I'll expand on the `doMath` example from above. Let's say that for whatever
reason, we often need to do this computation:

$$
x = \begin{cases}
3ab + 2c & \text{if } a < b \\
b + c & \text{otherwise}
\end{cases}
$$

This is the mathematical syntax that you'd see in a textbook, or off Wikipedia.
One challenge is to convert that format into code. We can see that it involves
variables `a`, `b`, and `c`, and what it does depends on their values. It
returns the result of a computation.

We can write the above math in Javascript like this:

```js
function doMath(a, b, c) {
  let x
  if (a < b) {
    x = 3 * a * b + 2 * c
  } else {
    x = b + c
  }
  return x
}
```

This lets us give a name to what we're doing. Admittedly, `doMath` is probably
not a great name. This just illustrates how you'd define it and (in a moment)
invoke it.

In this function, if `a` is smaller than `b`, we'll compute `3ab + 2c` and store
it in `x`. Otherwise, we'll store `b + c` in `x`. At the end, we _return_ `x`.

## Returning values

The `return` keyword does a couple things. First, it marks a place where the
function's result is going to be handed back to whatever code called it. So, the
`return x` becomes a _return statement_ (that's the keyword followed by an
expression that boils down to a value that serves as our result). Second, it
means that the function will be over the moment that value is returned. Once the
_return_ statement executes, the function stops. No more code in that function
will run.

It just so happens that my code above has a single return value at the very
bottom. This is a common pattern, but it isn't required. We could have written
the function like this, and it would behave the same way:

```js
function doMath(a, b, c) {
  if (a < b) {
    return 3 * a * b + 2 * c
  } else {
    return b + c
  }
}
```

In this rendition, we're returning one of those two expressions on the line
where they're computed. Notice also that we don't have an `x` variable declared
anywhere, and we're not assigning to it. This code returns the result of the
bare expression instead of the value contained in a variable.

Sometimes a function doesn't actually return a value. We informally call this a
"void function". Void functions are typically used for situations where the
function had some side effects, like drawing graphics, but didn't need to
calculate a value. Most void functions don't need an explicit `return`
statement, because when execution gets to the end of the function's code, the
function stops and it hands back control to whatever called it.

But there are situations where you'd want a void function to return earlier than
the end. In that case, you simply write `return` by itself, and the function
will end and give back control to whoever called it, as no result is needed.

```js
function drawSnow() {
  if (temperature >= freezing) {
    return // early return in this case
  }
  // code for drawing snow here reached only if
  // it is cold enough to freeze
}
```

### Void functions for doing work like drawing graphics

Functions that perform jobs for you instead of returning a computation are
common. You'll likely use them for drawing graphics. Here's a void function that
draws a circle at whatever `x, y` values we give it. Notice that this _always_
draws the dot in white, with a 25 pixel diameter. The important thing here is
that some details are up to the caller (providing x and y), and some details are
baked into the function definition (fill color and diameter).

```js
function drawDot(x, y) {
  push()
  fill("white")
  noStroke()
  circle(x, y, 25)
  pop()
}
```

This is also a decent example of how you'd defensively write a function that
doesn't change state persistently. It uses `push()` at the beginning to stash
the incoming graphics state, then it modifies graphics state (by filling white
and turning off drawing the stroke outline) and `pop()` at the end to restore
graphics state to what it started out as. Since there is no `return` statement
and we don't bail out halfway through, the push/pop pair both runs, and will
protect other code from inadvertently getting our graphics state changes.

## Variable Scope

Now that we've added functions to our programming tool belt, we need to talk
about variable scope. Variables are only available within some range of code. In
particular, variables that are defined inside functions are not available
outside of that function.

More generally, variables declared with `const` or `let` are only available in
the code block where they were declared. For top-level variables, that means the
whole file. For anything else, it means the code block, if-statement, or any
other curly-brace delimited group that we haven't yet seen, like loops.

<Callout intent="note">
  In the early days of Javascript we declared variables with the `var` keyword.
  This is still a valid but frowned-upon way to declare variables. A `var` is
  scoped to the entire function — so even if you declare one inside some inner
  curly braces, it will still be scoped to the entire function. This is a piece
  of historical curiosity that could bite you, so be careful to avoid `var`.
</Callout>

For example:

This might seem strange to newcomers, because you can see with your eyeballs
that, _clearly_, `midX` and `midY` have values. They're defined _right there_!
But, those values only make sense in the scope where they're defined, which here
is the `drawCenterGuide` function. If you want a function to be able to use
values that are defined in some other function, you'll have to pass that data in
as arguments. Similarly, if you compute data inside a function that must be used
outside of that function, just `return` that data.

You can also declare variables _outside_ of a function, which is common in p5
sketches. For example, right at the top of a sketch you might define a bunch of
variables, some with `const`, some with `let`, because that data must be used in
several places. It seems very convenient! For example:

```p5exercise autorun size="medium"
// sketch-level variables
const bg = "#202020"
const dotColor = "#802020"
let spot = 0

function setup() {
  createCanvas(150, 150)
  spot = width / 2             // no problem
}

function draw() {
  background(bg)               // no problem
  spot = mouseX
  fill(dotColor)               // no problem
  circle(spot, height / 2, 30) // no problem
}
```

Because `bg`, `dotColor`, and `spot` are all defined outside of any function,
you can reference them (and in the case of `spot`, modify them) inside `setup`,
`draw`, or any functions that you might define.

It might seem counter-intuitive, but variable scoping helps you out by making it
more clear what is available for use. When you have a bigger sketch, or even a
program with multiple files involved, there could be hundreds of variables, and
it would be confusing and overwhelming for them all to be available at all
places. If you happen to have access to a variable, you might just write to it,
thinking it harmless. But really you've just changed data that some other thing
needs.

You can think of function-scoped variables as holding your function's innermost
thoughts. When the function is done, those thoughts vanish into the aether. If
those variables were named things like `x` or `start` or other commonly used
names, you won't need to worry about polluting the larger scope with variables
that don't make sense in context, or would otherwise conflict. Feel free to name
your function-scoped variables however you like, as they only exist there.

With sketch-scoped variables you should be more careful, because they have more
visibility, so you should choose their names thoughtfully.

## Arrow functions

There is a newer syntax for writing functions, and since it involves the `=>`
token (equals sign followed by greater-than), we call them _arrow_ functions.
They look like this:

```js
const drawCenterGuide = () => {
  push()
  stroke("#ffffff30")
  const midX = width / 2 // scoped to the function
  const midY = height / 2 // same
  line(midX, 0, midX, height)
  line(0, midY, width, midY)
  pop()
}

const cube = (x) => x * x * x
```

Defining functions like this draws attention to the fact that functions
themselves are just a special type of value, and assigned into a variable like
any other value.

curly braces, as long as there's only a single expression as in the `cube`
definition above. In this case, don't use `return` - the expression's value will
be resolved and returned implicitly. But the moment you need more than one
expression, you're back to needing braces and using a return statement.

## Example

```p5exercise autorun size="medium"
function setup() {
  createCanvas(260, 170)
}

function draw() {
  background("#202020")

  // same y for all three; only the size changes as we move right
  //         x    y   w   h
  drawRobot(45, 110, 38, 46)
  drawRobot(130, 110, 38, 78)
  drawRobot(215, 110, 38, 28)
}

// x, y  -> center of the robot's body
// w, h  -> body width and height
function drawRobot(x, y, w, h) {
  push()
  rectMode(CENTER)
  stroke("#cfcfcf")
  fill("#6a7a8a")

  // body
  rect(x, y, w, h)

  // head sits on top of the body
  const headH = w * 0.6
  const headY = y - h / 2 - headH / 2
  rect(x, headY, w * 0.7, headH)

  // antenna
  line(x, headY - headH / 2, x, headY - headH / 2 - 8)

  // eyes
  noStroke()
  fill("#101010")
  circle(x - w * 0.15, headY, 5)
  circle(x + w * 0.15, headY, 5)

  // legs
  stroke("#cfcfcf")
  line(x - w * 0.25, y + h / 2, x - w * 0.25, y + h / 2 + 10)
  line(x + w * 0.25, y + h / 2, x + w * 0.25, y + h / 2 + 10)
  pop()
}
```

Given a single `drawRobot` function, we invoke it three times with different
parameters, and it draws three unique robots. Examine the structure of this
code, including how the function is defined, where the push/pop calls are made,
and how it is used with different numbers. You can use the same strategy in the
