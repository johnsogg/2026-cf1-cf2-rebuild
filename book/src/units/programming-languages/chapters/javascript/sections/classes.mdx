# Classes

> Intro: classes are like blueprints for making lots of things that share the
> same basic format: they all include the same member data (fields) and
> functions (methods). Given a single class you can make a zillion instances,
> and they are all independent.

> In this section we're going to look at classes by developing a type of digital
> creature called a Boid. Boids have history (need two sentences of history).

## The `class` keyword

> Think of a category of thing: cars, kitties, electronic medical records. These
> are all defined by their shape: what data they hold and what behaviors they
> exhibit. You can make a class to define that shape, and then create instances
> of that class that are independent. If you know an object's class, you know a
> lot about how to work with it.

> For example, we could make a class that represents students: you all have a
> major or two, optionally a minor, you have a student ID, you can enrol in or
> drop classes, you have some historical grades, and so on. That's the class for
> students. But you as an individual have your own _specific_ data: your major,
> your grades, your schedule.

## Instances

> Each Boid has its own color, its own position, its own heading. They are their
> own little people! Whenever we create objects based on classes, we call them
> _instances_. Each boid is independent, but they have the same fields and
> functions. We can say they have the same _type_, or _shape_.

> Each Boid has its own behavior in the form of functions that are defined
> inside the class block. Those functions are called `methods` in OO-speak, and
> when you use them, they operate on some particular instance. `move` is one
> such method; there is also `draw`. We will see many examples of methods later
> on.

> Each Boid can refer to its own personal data (its position, its color) using
> the `this` keyword. Whenever you see `this`, it means "the current object
> instance". Inside the `move` method, for example, we write `this.x` to refer
> to the X position of a particular Boid. Data fields associated with instances
> are called `members` in object-oriented vernacular.

> Classes work nicely with graphics contexts because they compartmentalize the
> data for various unique items, while recognizing that many of those items also
> share structure. So we create a class for Boids, and then use it to create
> many independent Boids.

## File organization - one class per file

> It is common but not required to put classes in their own files. For example,
> `boid.js` should contain a `Boid` class. Good naming conventions can make your
> life easier because you can find code faster. It also helps to prevent you
> from reaching into other classes when you don't intend to (creating what
> programmers affectionately call "spaghetti code", owing to the mess of
> connections between them).
