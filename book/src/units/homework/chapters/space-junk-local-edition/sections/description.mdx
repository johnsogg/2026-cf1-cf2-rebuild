# Space Junk, Local Edition

This homework revisits the
[Space Junk homework](/homework/space-junk-game/description). The purpose of the
first one was to have you write code to a spec, rather than following your own
creative instincts.

The purpose of this evolution of the homework is to kick off the p5.js web
editor training wheels by working from a locally edited git repository. This
will be a different way of working, and you will likely find it uncomfortable.

In this homework, you will (1) port your earlier homework to be managed in a git
repository. You'll then (2) edit the code with a local editor, and (3) round out
the game with a little more code.

## Why work locally?

Writing code locally gives you access to a host of additional tooling beyond the
p5 web editor:

- Use your choice of editor (of which there are many options)
- Source control for easily creating save points
- ... and for collaborating with others
- Automated testing
- Automated code checking ("linting")
- Automated code formatting
- Access to the full capabilities of your computer beyond the browser
- Install and use 3rd party libraries easily with package managers
- Configure everything to work as you want

If you're just starting to code, most or all of this might not seem particularly
compelling. I get that, and my response is probably not super satisfying: you'll
learn to appreciate the added control these tools give you, and through them,
you'll learn a lot about how computers actually work.

Above, I mentioned several reasons to work locally, but for now we're only going
to add git into the mix. Testing, linting, and package management are not in
scope here. Of course, you can go the extra mile(s) if you want to start using
those things!

## Install an editor and a git client

You can install any code editor you want. I recommend
[VS Code](https://code.visualstudio.com/), though it is laden with AI that will
want to do your homework for you. Find a way to turn all that off.

You'll also need a git client. There are many, but for consistency I'll
recommend [GitHub Desktop](https://code.visualstudio.com/). I don't personally
use it aside from showing students how to use it - I use the command line `git`
client. You will need to sign in to your GitHub account with this in order to
see your repositories.

### Commit early, commit often

Your starting point is wherever you left off in the first homework: a game where
junk can be caught in the beam, but then just vanishes. You'll add two more
phases, continuing the numbering from before. Each phase should end with a
commit and a push.

A commit is a save point, and the best time to make one is when you've gotten
something working. Do this often, and try to develop a habit of it. Write a
summary that tells future-you what changed, like "Phase 4: carry junk to the
Mothership". Avoid summaries like "stuff" or "asdf", which save time now but are
also kinda dumb and unhelpful. After committing, the button at the top right
changes from 'Publish branch' to 'Push origin'. Press it to send your commit to
GitHub, just like what we did with the original batch.

If you switch to the History tab in GitHub Desktop, you'll see each of your
commits listed, and you can click on any one to see exactly which lines changed.
That list is the record of how your project evolved.

## Phase 4: Deliver the junk (3 points)

So far, junk you catch in the beam just disappears. Now the Magpie is going to
carry it to the Mothership and drop it off, and you'll get points for it.

You'll edit these functions:

- `Magpie.captureJunk`
- `Magpie.draw` (the part marked for Phase 4)
- `Game.resolveDropoff`
- `Game.updateScore`

Search for `TODO (Phase 4)` comments in the code at each of these. Your game
already calls these in the right places; it's just that they don't do anything
yet.

### Carrying the junk

When `Game.move` catches a piece of junk, it calls `Magpie.captureJunk(junk)`.
Your job is to remember that junk in `this.capturedJunk`, and to turn off the
beam. A Magpie that is hauling cargo can't also be tractoring more, and
`enableBeam` is already written to refuse to turn the beam back on while
`capturedJunk` is set.

Then, in `Magpie.draw`, show the junk hanging below the ship. It should be drawn
before the Magpie so the ship is on top. The junk needs to follow the ship
around as it turns, so rather than computing where it goes, do what we did for
everything else: set up the transforms so you can draw as though the Magpie were
at `(0, 0)` pointing up. Inside a `push()` and `pop()`, rotate by the Magpie's
rotation, translate to `(0, Magpie.CARGO_Y)`, and call `Junk.drawJunk()`. If
that sounds like a lot of moving parts, review the
[Geometry section](/programming-languages/building-with-code/geometry).

The `push` and `pop` matter here. Without them, your translate and rotate would
also apply to the Magpie you draw next, and the ship would end up in the wrong
place.

### Dropping it off

Delivery works much like catching. The Magpie has to hold the junk inside the
Mothership's pickup circle for a little while. You can see this circle by
pressing `~` to turn on debug mode.

`Game.resolveDropoff(delta)` is called every frame, and returns `true` when the
junk is delivered. It is the same idea as `resolveBeam`, but there is only ever
one junk to worry about:

_If the Magpie isn't carrying junk, return false. If the carried junk is within
`Mothership.PICKUP_DIAMETER / 2` of the Mothership, add `delta` to the junk's
`dropoffTime`. Otherwise, reduce `dropoffTime` by `delta`, but not below zero.
Return true if `dropoffTime` is more than `Game.JUNK_DROPOFF_TIME_MS`._

p5's `dist()` function will help you measure the distance between two points.
The junk's position is in `junk.physics`, and the Mothership's is in
`this.mothership.physics`.

You may wonder how the carried junk has a position when it was removed from the
level's list. It still has a `Physics` object, and `Magpie.move` updates it to
the cargo spot every frame. So as far as your distance calculation is concerned,
the junk is wherever it's drawn.

Once `resolveDropoff` returns true, `Game.move` clears the Magpie's cargo and
calls `updateScore("dropoff")`. Fill that function in so a dropoff adds
`Game.SCORE_DROPOFF` to `this.score`. You won't see the score on screen until
the next phase, but you can check it with `console.log` if you'd like.

### Done when

- Caught junk rides below the Magpie, and stays below it as the ship turns
- The beam turns off when you catch something, and can't be turned on while
  carrying
- Hovering over the Mothership for about a second delivers the junk, and the
  beam works again afterward
- Moving away before time is up doesn't deliver, and drains the timer slowly
- Once all junk has been delivered, you see "All clear!"
- You made a commit and pushed it to GitHub

## Phase 5: Timer, score, and lives (2 points)

The game works, but the player can't see how they're doing. This phase adds the
heads-up display (the "HUD"), which is the timer, the score, and the number of
spare ships.

You'll edit these:

- `timeToStringParts` in `utils.js`
- `Level.timeLeft`
- `Level.draw`

### The timer

`Level.timeLeft` gives the milliseconds remaining: the level's initial time
minus the elapsed time. It should never go below zero, so that the display
doesn't count into negative numbers.

Then `timeToStringParts` turns milliseconds into something to show. It returns
an object with two strings, `minutes` and `seconds`. A time of 125,000 ms
becomes `{ minutes: "2", seconds: "05" }`. Two things to note:

- Round _up_ to whole seconds first. A clock that says `0:00` should mean time
  is really up, not that there's still half a second left. `Math.ceil` is your
  friend.
- Seconds always have two digits. JavaScript strings have a `padStart` method
  that might come in handy.

### Drawing the HUD

In `Level.draw`, draw the HUD before the junk, so it sits underneath all the
game objects. Use `Level.HUD_TEXT_SIZE` and `Level.HUD_PAD` for the text size
and margins.

- **Timer**: top left, as `minutes:seconds`
- **Score**: top right, in the same style as the timer
- **Lives**: bottom left, one small Magpie for each _spare_ life. The Magpie you
  are currently flying is not a spare, so draw `lives - 1` of them.

For the lives, `Magpie.drawMagpie()` draws around `(0, 0)`, so you'll need to
`translate` to where you want it and `scale` it down by `Level.LIVES_SCALE`.
Start `Level.LIVES_PAD_LEFT` from the left edge and `Level.LIVES_PAD_BOTTOM`
from the bottom. Each ship after that goes `Level.LIVES_GAP` further to the
right, measured center to center. Wrap each one in `push` and `pop` so the
transforms don't pile up.

There is no game over in this version of the game, so don't worry about what
happens when time runs out or lives hit zero. It's OK if the timer sits at
`0:00`.

### Done when

- The timer counts down from 2:00, and stops when you see "All clear!"
- The score is shown, and goes up by 100 each time you deliver junk
- Two small Magpies are shown at the start
- You made a commit and pushed it to GitHub
